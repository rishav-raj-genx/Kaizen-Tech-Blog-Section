Introduction

Version Control is a system that records changes made to files over time. It allows developers to track modifications, restore previous versions, and collaborate efficiently on software projects. Without version control, managing changes becomes difficult, especially when multiple developers work on the same project.

Git is a distributed Version Control System (VCS) developed by Linus Torvalds in 2005. It enables developers to work independently, maintain project history, and merge changes safely. Git is lightweight, fast, and one of the most widely used version control systems in the software industry.

Note

Git is the Version Control System, while GitHub is a cloud platform used to host Git repositories and collaborate with other developers.

Why Version Control?

  • Tracks every change made in a project.
  • Allows multiple developers to work together.
  • Provides complete project history.
  • Enables rollback to previous versions.
  • Reduces chances of losing important work.

Git Basics

Git is a distributed Version Control System (VCS) that helps developers track changes in source code during software development. It records every modification made to a project, allowing developers to review previous versions, restore deleted files, and collaborate efficiently with teams. Unlike traditional version control systems, Git stores the complete project history on every developer's machine, making it fast, reliable, and capable of working even without an internet connection.

Whether you are working on a personal project or contributing to a large enterprise application, Git provides a structured workflow that helps maintain code quality and prevents accidental data loss. Today, Git has become the industry standard for software development and is widely used by companies and open-source communities around the world.

Key Features of Git

  • Distributed Version Control System.
  • Stores complete project history.
  • Works both online and offline.
  • Fast and lightweight.
  • Supports collaboration among multiple developers.
  • Open-source and completely free.
  • Provides branching and merging capabilities.
Did You Know?

Git was created by Linus Torvalds in 2005 to manage the development of the Linux kernel. Today, millions of developers use Git for software development.

Installing Git

Before using Git, it must be installed on your operating system. Git is available for Windows, macOS, and Linux.

After installation, verify that Git is correctly installed by running the following command in the terminal.

If Git is installed successfully, the terminal will display the installed Git version.

Frequently Used Git Commands

Command Description
git init Creates a new Git repository.

Practical Example

The following example demonstrates how to create a new Git repository and make the first commit. 

mkdir GitDemo
cd GitDemo
git init
touch index.html
git add .
git commit -m "Initial Commit"

In this example, a new project folder is created, Git is initialized, an HTML file is added, the changes are staged, and the first commit is created.

Beginner Tip

Always execute git status before creating a commit. It helps verify which files are staged, modified, or untracked.

Common Mistakes Beginners Make

  • Writing unclear commit messages.
  • Initializing Git in the wrong folder.
  • Making unnecessary commits for very small changes.
  • Ignoring the output of git status.

Branches

A branch in Git is an independent line of development that allows developers to work on new features, bug fixes, or experiments without affecting the main project. Branches make collaboration easier because multiple developers can work on different tasks simultaneously without interfering with each other's code.

The default branch in most repositories is called main (older repositories may use master). Developers usually create a new branch for every feature or bug fix and merge it back into the main branch after testing.

Why Use Branches?

Branches keep the main project stable while allowing developers to build and test new features independently.

Benefits of Using Branches

  • Develop multiple features simultaneously.
  • Fix bugs without affecting production code.
  • Test experimental ideas safely.
  • Simplifies collaboration in teams.
  • Makes code review easier before merging.

Merge

Git Merge is a feature that combines changes from one branch into another. After developers complete their work on a feature branch, the branch is merged into the main branch so that the new code becomes part of the project. Merging preserves the complete history of development while integrating new features safely.

Git provides different merge strategies depending on the project history. The two most common merge strategies are Fast-Forward Merge and Three-Way Merge. Understanding these strategies helps developers maintain a clean and organized project history.

Important

Always review your code and ensure the feature branch is tested before merging it into the main branch.

Why Do We Use Merge?

  • Combines completed features into the main branch.
  • Allows multiple developers to work independently.
  • Maintains complete project history.
  • Helps integrate bug fixes safely.
  • Supports collaborative software development.

Types of Merge

Feature Fast-Forward Merge Three-Way Merge
Definition Moves the branch pointer forward without creating a new merge commit. Creates a new merge commit to combine changes from both branches.
Merge Commit No Yes
Branch History Linear history. Preserves the history of both branches.
When Used When the target branch has no new commits. When both branches contain independent commits.
Complexity Simple and straightforward. Slightly more complex but preserves complete history.
Quick Tip

Use a Fast-Forward Merge whenever possible for a clean, linear history. Use a Three-Way Merge when both branches have new commits and you want to preserve the complete development history.

Practical Example

git switch main

git merge feature-login

git push origin main

In this example, the developer switches to the main branch, merges the feature-login branch, and then uploads the updated repository to GitHub.

Best Practice

Pull the latest changes from the remote repository before performing a merge. This reduces the chances of merge conflicts.

Common Mistakes

  • Merging an untested branch.
  • Ignoring merge conflicts.
  • Deleting a branch before verifying the merge.
  • Merging outdated branches without pulling recent changes.
  • Working directly on the main branch instead of using feature branches.

Interview Questions

Q1. What is Git Merge?

Git Merge is the process of combining changes from one branch into another while preserving project history.

Q2. What is the difference between Fast-Forward Merge and Three-Way Merge?

A Fast-Forward Merge moves the branch pointer forward without creating a new merge commit because there are no separate changes between the branches. In contrast, a Three-Way Merge creates a new merge commit when both branches have independent changes, preserving the complete history of the project.

Pull Requests

A Pull Request (PR) is one of GitHub's most important collaboration features. It allows developers to propose changes made in one branch and request that they be reviewed before being merged into another branch. Pull Requests improve code quality by enabling discussions, code reviews, and automated testing before changes become part of the main project.

In professional software development, developers rarely merge code directly into the main branch. Instead, they create a Pull Request so that teammates can review the code, suggest improvements, and approve the changes.

Important

A Pull Request does not immediately merge your code. It first allows reviewers to examine your work and provide feedback before approval.

Why Use Pull Requests?

  • Improves code quality through peer review.
  • Encourages team collaboration.
  • Helps detect bugs before merging.
  • Maintains a clean and stable main branch.
  • Provides a complete discussion history for every change.

The GitHub Workflow is a standard development process followed by developers and software teams to build features, fix bugs, and collaborate efficiently. Instead of working directly on the main branch, developers create feature branches, make changes, review code through Pull Requests, and finally merge approved changes into the main branch.

Following a structured workflow keeps the repository organized, minimizes merge conflicts, and ensures that every change is reviewed before becoming part of the project.

Fork

A Fork is a personal copy of someone else's GitHub repository. It allows you to experiment with code, add new features, or fix bugs without modifying the original project. Forking is widely used in open-source development because contributors usually do not have direct write access to the original repository.

When you fork a repository, GitHub creates a complete copy under your own account. You are free to make changes in your fork and later contribute those changes back to the original repository through a Pull Request.

Did You Know?

Forking does not affect the original repository. It creates an independent copy that belongs to your GitHub account.

Why Do We Use Fork?

  • Contribute to open-source projects.
  • Experiment without affecting the original project.
  • Create your own copy for learning purposes.
  • Safely develop new features.
  • Submit changes using Pull Requests.

How to Fork a Repository

  1. Open the GitHub repository.
  2. Click the Fork button in the top-right corner.
  3. Wait for GitHub to create a copy in your account.
  4. Clone your forked repository to your local machine.
  5. Start making changes in your own repository.

Example

Suppose you want to contribute to the Kaizen Tech Blog Section repository. Since you do not have direct access, you first fork the repository into your GitHub account. After making changes, you push them to your fork and create a Pull Request so the maintainers can review your work.

Clone

Cloning is the process of creating a local copy of a Git repository from a remote server such as GitHub. It downloads all project files, branches, commit history, and repository configuration to your computer, allowing you to work on the project locally.

Unlike downloading a ZIP file, a cloned repository remains connected to the remote repository. This enables you to pull the latest changes, push your own commits, and collaborate efficiently with other developers.

Important

A cloned repository contains the complete commit history and remains linked to the original remote repository.

Why Do We Use Clone?

  • Download a GitHub repository to your computer.
  • Start working on an existing project.
  • Collaborate with team members.
  • Maintain synchronization with the remote repository.
  • Access the complete commit history.

.gitignore

A .gitignore file tells Git which files and folders should be ignored and not tracked in the repository. It is commonly used to exclude temporary files, build outputs, log files, operating system files, and sensitive information such as API keys or passwords.

Using a .gitignore file keeps the repository clean, reduces unnecessary files, and prevents confidential data from being accidentally uploaded to GitHub.

Important

Files listed in the .gitignore file are ignored only if they have not already been tracked by Git.

Why Use .gitignore?

  • Prevents unnecessary files from being committed.
  • Protects sensitive information from being uploaded.
  • Keeps the repository clean and organized.
  • Reduces repository size.
  • Makes collaboration easier by excluding machine-specific files.

If a file has already been committed before adding it to .gitignore, Git will continue tracking it. To stop tracking the file, remove it from the Git index first. 

git rm --cached filename

git commit -m "Stop tracking file"
Best Practice

Create a .gitignore file at the beginning of a project so that unnecessary files are never added to the repository.

Common Mistakes

  • Adding sensitive files after they have already been committed.
  • Forgetting to create a .gitignore file at the start of the project.
  • Ignoring important project files by mistake.
  • Assuming .gitignore removes files already tracked by Git.

Interview Questions

Q1. What is a .gitignore file?

A .gitignore file specifies which files and directories Git should ignore and not include in version control.

Q2. Does .gitignore remove files that are already tracked?

No. Files already tracked by Git must first be removed from the Git index using git rm --cached before .gitignore can prevent them from being tracked in future commits.

Quick Summary

The .gitignore file is an essential part of every Git project. It keeps repositories clean, protects sensitive information, and ensures that only necessary project files are tracked by Git.

Merge Conflicts

A Merge Conflict occurs when Git is unable to automatically combine changes from two different branches because the same part of a file has been modified differently. Git pauses the merge process and asks the developer to manually resolve the conflict.

Merge conflicts are a normal part of collaborative software development. They do not indicate an error in Git; instead, they require the developer to decide which changes should be kept.

Important

A merge conflict happens only when Git cannot determine which version of the code should be used automatically.

When Do Merge Conflicts Occur?

  • Two developers edit the same line of a file.
  • One developer deletes a file while another modifies it.
  • Different branches contain incompatible changes.
  • Branches remain separate for a long period before merging.

Git marks the conflicting changes using special symbols. The developer must edit the file, choose the correct content, remove the conflict markers, and save the file.

Resolving a Merge Conflict

  1. Open the conflicted file.
  2. Review both versions of the code.
  3. Edit the file and keep the correct changes.
  4. Remove the conflict markers.
  5. Stage the resolved file.
  6. Commit the merge.

Useful Commands

git commit -m "Resolved merge conflict"

How to Avoid Merge Conflicts

Best Practice Benefit
Pull changes regularly. Stay updated with the latest code.
Create small feature branches. Reduces overlapping changes.
Commit frequently. Makes conflicts easier to resolve.
Communicate with teammates. Avoids editing the same code simultaneously.
Best Practice

Resolve conflicts carefully instead of simply choosing one version. Review both changes to ensure that no important code is lost.

Common Mistakes

  • Deleting code without reviewing both versions.
  • Leaving conflict markers in the file.
  • Forgetting to stage resolved files.
  • Creating one large merge after weeks of development.

Interview Questions

Q2. How can merge conflicts be avoided?

Merge conflicts can be reduced by pulling changes regularly, creating small feature branches, committing frequently, and communicating with team members.
